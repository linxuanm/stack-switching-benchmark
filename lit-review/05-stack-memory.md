# Stack memory: growth, segmentation, copying, shrinking

Condensed from `fx-research` note 06.

The literature does not use "stack compression" as a term of art. What it has is a
well-developed set of answers to a closely related question: **how do you give N suspended
computations a stack each without paying N × (worst-case stack size)?**

## 1. The governing invariant

> **You may relocate a stack if and only if nothing outside it holds a pointer into it — or you
> can find and rewrite every such pointer.**

Everything else follows.

| System | Interior pointers? | Consequence |
|---|---|---|
| **OCaml** | never generated by the compiler | fibers can be `realloc`'d and copied; only **two** words need patching |
| **Go** | yes, but the runtime knows every frame layout | stacks are copied *and* **pointers into them rewritten** during the copy |
| **JVM/Loom** | no raw interior pointers; frames are GC-described | frames can be **frozen into a heap object** and thawed elsewhere |
| **C / C++ / Rust** | yes, and indistinguishable from other integers | **cannot move a stack.** libhandler goes to the length of restoring frames *to the same addresses* on resume |
| **Wasm engine stack** | not addressable from Wasm — but engines interleave host/C++ frames | movable in principle; not in practice today (also why multi-shot is hard) |
| **Wasm shadow stack** (linear memory) | **yes** — any address-taken local, `alloca`, or aggregate | **cannot be moved or compacted.** This is the hard part |

**The corollary that matters for a Wasm project: the thing you most want to shrink (the
per-coroutine shadow-stack region in linear memory) is the thing you are least able to move.**

## 2. The five strategies

### (a) Fixed-size contiguous
Allocate a block per coroutine at creation. Simple, zero runtime management, best sequential
performance. **Cost: you must guess.** Guess high and you waste; guess low and you overflow.

WasmFX/Wasmtime prototype: **4096 bytes per coroutine** → **55.5 MB** vs **13.4 MB** for a
bespoke state machine at 10 000 live coroutines, a **4×** penalty attributed entirely to this
choice. Note also the distinction between *unsafe* fixed stacks (`malloc`'d, no guard page ⇒
**silent** overflow into the heap) and *safe* ones (`mmap`'d with guard pages).

### (b) Resizable contiguous (copy-and-double)
Start small; on overflow allocate 2× and **copy**. Amortized O(1) growth, and you get to pick a
genuinely small initial size.

- **OCaml 5 fibers**: initial frame area 16 words, doubling, `malloc` + a stack cache. Cost is in
  *code size* (+19% / +30% text).
- **Effekt LLVM backend**: same doubling-realloc, made safe by routing every reference through a
  **stable prompt** rather than a raw stack address.
- **Go**: contiguous since 1.3, starting at 2 KB, doubling, `morestack` prologue check.
- **Farvardin & Reppy pick this as the space-efficiency winner** over segmentation, *"because the
  segment size is constant"*.

### (c) Segmented (stacklets)
Fixed-size segments in a linked list; `morestack` on overflow. No relocation, so it works with
interior pointers. Used by Bruggeman/Waddell/Dybvig (1996), libseff, and formerly Go and Rust.

**The hot-split problem** is why Go and Rust abandoned it. libseff's measurement — a call that
always needs a new segment, 10⁸ iterations, sweeping real work in the callee:

| multiplications in callee | 0 | 5 | 10 | 15 | 20 |
|---|---|---|---|---|---|
| native C | 1.27 | 1.00 | 1.00 | 1.00 | 1.00 |
| libseff, fixed stack | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 |
| libseff, **hot split (recycled segments)** | **10.92** | 2.25 | 1.29 | 1.00 | 1.00 |
| libseff, **hot split + free each segment** | **33.94** | 6.91 | 3.83 | 2.69 | 2.17 |

Three separate findings: (1) worst case ~11×, but **13 floating-point multiplies of real work
erase it** — hot split is a microbenchmark problem more than a production one, and it only shows
up if the function isn't inlined; (2) **recycling segments instead of freeing them is worth
3–34× — segment reuse is not an optimization, it is the design**; (3) standard library functions
are precompiled without overflow checks, so calls into them can overflow silently (libseff's
answer is a macro that switches to the system stack instead).

### (d) Virtual-memory overcommit ("grow in place, never move")
Reserve a large virtual range per stack; commit physical pages lazily on fault. The stack grows
in place, so **addresses stay valid** — the only growth strategy compatible with interior
pointers.

- **libmprompt / libmpeff** (Leijen & Sivaramakrishnan) is the reference implementation.
  *gstacks*: reserve up to **8 MiB** of address space, **commit only 4 KiB** initially, grow on
  demand. A *gpool* carves one large region into fixed-size slots with **no-access gaps between
  them for overflow detection**, computes stack addresses from indices so slots are reusable, and
  keeps per-thread caches with deferred deallocation. **64-bit only.** The WasmFX paper names
  this as the promising direction for Wasmtime.
- **The 2025 Edinburgh study** (Yu, *Evaluate the Stack Management in Effect Handlers using the
  libseff C Library*) implements and compares fixed / segmented / **kernel-level overcommit** /
  **user-level overcommit** inside libseff:
  - On *plain context-switch latency*, fixed and segmented win; overcommit adds management
    overhead (user-level worst).
  - Once real work is added the gap closes, and at 10 000 iterations **kernel overcommit slightly
    beats fixed and segmented**.
  - On *dynamic stack expansion*, **kernel overcommit is clearly best**; segmented is worst.
  - Conclusion: *"no single stack management strategy is suitable for all scenarios"*; kernel
    overcommit is the best general balance.
  - Honest limitations: batch commit **trades granularity for fewer faults and over-allocates**;
    SIGSEGV+`mprotect` is **non-deterministic under concurrency**; microbenchmarks only.

### (e) Heap-allocated frames (CPS / linked)
No stack at all; the GC handles everything. Perfectly space-efficient and trivially multi-shot.
Loses on sequential performance and is invisible to debuggers. `cps` is the simplest runtime by
far; `linked` (mutable heap frames) *"should always be avoided"*.

## 3. Copy-out-on-suspend: the closest thing to actual compression

The one production design that literally shrinks a suspended stack to its live size is **JVM
Project Loom**.

- A virtual thread's stack lives in the Java heap as a **`StackChunk`** — a heap object holding
  an integral number of frames **copied verbatim** from the carrier thread's platform stack.
- **`freeze`** on yield: copy live frames off the native stack, release the carrier stack.
  **`thaw`** on mount: copy back.
- **Lazy copying**: thaw only the frames you need now. If the frozen stack fits the existing
  chunk, the chunk is **reused in place** — a bulk memcpy with no allocation and no GC work.
  (Caveat: fast reuse only works while the chunk is in the young generation.)
- Result: a virtual thread's footprint **starts at a few hundred bytes** against a platform
  thread's megabyte-scale stack.

This works because the JVM has exact frame metadata and no raw interior pointers.

**Go's variant:** goroutine stacks are **shrunk during a GC cycle** — if live use is under ¼ of
the current stack, allocate half the size and copy, floor 2 KB. Both directions rewrite interior
pointers, which the runtime is *allowed* to do because it knows every frame's layout.

## 4. The design space for Wasm

Sorted by how much of the §1 invariant they need. Where upstream Wasmtime stands on each is in
[04-runtimes.md](04-runtimes.md) Part II §5.

**Needs nothing (works today):**

1. **Pool and recycle stacks.** Already worth 68× on `c10m`. Wasmtime's tracking issue lists
   "unify stack switching with fiber stacks and the pooling allocator" as open work, and the
   pooling code already exists one directory over.
2. **Right-size at creation.** If the producer knows the maximum stack depth of a coroutine body
   — and for compiled generators and async functions it very often does statically — the engine
   could take a size hint rather than a fixed default. **This is the cheapest available win and
   nobody seems to have proposed it.**
3. **Reserve-and-commit-on-demand** (libmprompt gstacks). Grows in place, never moves, so it is
   compatible with the shadow stack *if* the shadow stack can be given its own address range.
   Historically limited by 32-bit linear memory — but **Memory64 shipped in WebAssembly 3.0
   (2026)**, so this is now an option that did not exist when the WasmFX paper was written.

**Needs "no interior pointers into this region":**

4. **Copy-and-double** (OCaml/Go/Effekt style) for the engine stack only.
5. **Loom-style freeze/thaw** for the engine stack: on `suspend`, copy live frames out to a
   right-sized heap object; on `resume`, thaw lazily. The engine *does* know Wasm frame layouts
   (it already emits stack maps), so this is more plausible than most people assume — and it
   yields **multi-shot for free**, since copy = clone.
6. **Shrink on suspend / during GC** (Go's `shrinkstack`). A suspended continuation is exactly the
   moment when you know how much stack is live.

**Needs new mechanism:**

7. **Splitting the shadow stack. The real prize.** Options: a per-coroutine shadow stack that is
   itself segmented; a compiler pass that proves which frames have no address-taken locals and can
   therefore live on the (relocatable) engine stack; or a Wasm-level notion of a relocatable
   region with a base register the toolchain must go through. Note the analogy to Effekt's
   **stable prompts** and Ma/Jung/Zhang's **virtual addresses + software MMU** — both solve
   "references into a stack that may move" by inserting a stable indirection.
8. **`cont.clone` / multi-shot**, blocked by the same invariant.

**The recurring pattern:** every solution to "the stack may move" is a **stable indirection** —
Effekt's prompts, Loom's chunk handles, Go's pointer rewriting, Zhang's virtual addresses, Wasm's
fat-pointer revision counters. If you design stack compression for Wasm, you are designing an
indirection and choosing where to pay for it.
